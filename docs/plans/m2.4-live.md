# M2.4 (Live) — Implementation Plan

**How to use this plan:** tasks are ordered and each ends with a commit. Work them in sequence;
each leaves the tree working and testable. Record what actually happened on an "Actual:" line.

**Goal:** make the editor *live and correct* — able to be woken by something other than a
keypress, able to notice the file changing underneath it, and able to save without quietly
destroying what it did not write.

**Why this exists as its own milestone.** Gap analysis Part 6 scoped all of this as "M2.5"
alongside tree-sitter, `typ-config` and themes-as-files. That is three milestones wearing one
number, and the bundling is actively harmful: the event-loop rework is the riskiest change in
the project so far, and tying it to the largest new subsystem means neither half can ship if
either goes badly. Split at the seam that was already there — everything here is about the
editor being live and correct, and none of it needs a theme. Colour is M2.5, and it depends on
this milestone's channel existing, which is the honest direction of that dependency.

**The reordering inside it, stated because gap analysis says otherwise.** Defect 31 says file
watching "should be M2.5's first task, not its last", and it is right about the priority — it
is a data-loss bug. It cannot literally be first: a watcher is a worker thread, and a worker
thread that cannot wake the event loop delivers nothing until the user's next keypress. The
channel is its prerequisite, so the channel is Task 1 and watching is Task 2. Nothing else
comes before them.

**Spec:** [`../design/architecture.md`](../design/architecture.md) — §4 "no blocking work on
the render thread" and the budget table, §7 the render and input model (damage-driven redraw,
input coalescing, the single blocking channel).

**Prior plan:** [`m2.3-polish.md`](m2.3-polish.md). `main` is v0.2.3, 453 tests green on three
platforms.

## Global constraints

Every task's requirements implicitly include the M2 plan's "Global constraints". Additionally:

- **Nothing blocks the render thread.** This milestone is the one that makes that invariant
  *true* rather than merely uncontradicted — today it holds only because nothing runs
  off-thread yet.
- **A redraw happens because state changed, never because the loop went round.** Once Task 3
  lands, anything that changes what is on screen and does not say so is an invisible bug. That
  is the whole risk of this milestone and every task after Task 3 carries it.
- **No test may sleep to synchronise.** A watcher test that waits 200 ms is a test that fails
  on a loaded CI runner and gets deleted. Wait on the channel with a timeout, and let the
  timeout be the failure.
- **The keystroke budget does not move.** `InsertChar` is 1.9–3.9 µs and a frame is 439 µs on a
  50k-line file. Damage-driven redraw should *improve* both; a regression means the dirty
  tracking is doing more work than the unconditional repaint it replaced.

## What M2.4 does not include

No tree-sitter, no `typ-config`, no themes as files, no capability detection, no
`.editorconfig`: all M2.5, and all of them want the worker channel this milestone builds. No
tabs, splits, resizable panels, or command palette: M4. Non-UTF-8 file support stays at M4 with
config, because an encoding setting is what makes it worth anything.

## Task 1: One channel the loop blocks on

The enabling change, and the riskiest in the project so far. Everything else in this milestone
and most of M2.5 is waiting on it.

**Files:** modify `crates/typ-core/src/event.rs`, `crates/typ-app/src/run.rs`, add
`crates/typ-app/tests/wakeup.rs`

### The design, decided here

`run.rs` calls `event::read()`, which blocks until the *terminal* has something. Anything a
worker produces — a finished parse, an LSP response, a file-change notification — therefore
does not appear until the user happens to press a key. Architecture §7 names this and names the
fix: **the loop blocks on one channel**, with a thread pumping crossterm into it.

The M0 spike tried the other repair — `event::poll(16ms)` plus a dirty flag — and recorded it
as a known ceiling: it wakes 60 times a second forever to do nothing. That is acceptable for a
30-second spike and not for an editor someone leaves open.

```rust
enum AppEvent {
    Input(crossterm::event::Event),
    FileChanged(PathBuf),
    // M2.5 adds Parsed(Tree) here, and M3 adds Lsp(Response). That is the point.
}
```

- [ ] **Step 1 (RED): a worker wakes the loop with no keypress**

The test that could not be written before: hold the sender, send an `AppEvent` from another
thread, and assert the loop processes it **without any terminal input at all**. Today's loop
cannot pass this, because it is blocked inside `event::read()`.

Drive the loop's body rather than `run()` itself — `run()` owns the terminal and a test has no
tty. Extract the body as something a test can step: one function taking an event and returning
whether to continue.

- [ ] **Step 2 (GREEN): the pump thread and the channel**

`std::sync::mpsc`, not a new dependency. One thread doing `event::read()` in a loop and
forwarding; the main loop receiving. The pump thread ends when the receiver is dropped, which
is what stops it outliving the editor.

**The trap:** the pump thread cannot be joined on exit, because it is parked inside a blocking
`event::read()` that only returns when the user presses something. Detach it and let process
exit collect it. Trying to join is a hang on quit, and it will look like the editor has frozen.

- [ ] **Step 3: a handle workers can hold**

`AppEvent` senders are cloneable and handed to workers. This is the seam Task 2 plugs into and
the one M2.5 and M3 plug into, so it is worth being deliberate: the sender is the *only* way a
worker talks to the app, and no worker gets a reference to `App`.

- [ ] **Step 4: commit** — `feat(app): block on one channel so a worker can wake the loop`

## Task 2: The file on disk changed

Defect 31, and the reason this milestone is ordered the way it is. **This is a data-loss bug**:
a rebase, a formatter, or another editor changes the file while it is open, TYPE neither
reloads nor warns, and the next save silently overwrites the lot.

**Files:** add `crates/typ-buffer/src/watch.rs`, modify `app.rs`, add
`crates/typ-app/tests/external_change.rs`

### The dependency, checked

`notify` — cargo resolves **8.2.0** stable (9.0 is at rc.4; do not take an RC for this). The
workspace has no equivalent and no crate that could grow into one. It is the standard Rust
watcher, uses the OS mechanism on each platform (inotify, kqueue, ReadDirectoryChangesW), and
TermIDE carries a whole `watcher` crate around it.

**Take `notify` alone, not `notify-debouncer-full`.** Debouncing here is four lines against a
second crate at `0.8.0-rc.2`, and the debounce this needs is not the general one — see Step 2.

### The decision, decided here

Three states, and only one of them is automatic:

| Buffer | On external change | Why |
|---|---|---|
| Clean | **Reload silently** | There is nothing to lose and nothing to ask about. This is what makes `git rebase` in another pane not a chore. |
| Dirty | **Warn, change nothing** | Both versions matter and only the user knows which. Reloading discards their edits; ignoring discards the other write on next save. |
| Deleted | **Warn, keep the buffer** | The buffer is now the only copy. Saving recreates the file, which is almost certainly what was wanted. |

- [ ] **Step 1 (RED): an external write to a clean buffer is picked up**

Write a file, open it, write to it again from the test, and assert the buffer contains the new
text — with **no keypress in between**, which is the half that needs Task 1.

Wait on the app's channel with a timeout rather than sleeping. A watcher test that sleeps 200 ms
is a test that fails on a loaded runner and then gets deleted.

- [ ] **Step 2 (RED): a dirty buffer is never silently reloaded**

Type into the buffer, write the file externally, and assert the buffer still holds **the user's
text** and the status bar says the file changed on disk. This is the test the whole task exists
for.

**Our own save must not trip it.** `save()` writes the file, the watcher reports the write, and
a naive implementation reloads the buffer from the file it just wrote — harmless when it works
and a race when it does not. Ignore events whose contents match what we just wrote, or record
the save's own mtime and skip that event. Decide it here rather than discovering it as a flake.

- [ ] **Step 3 (GREEN): the watcher**

A worker thread holding the `notify` watcher, sending `AppEvent::FileChanged` down Task 1's
channel. Watch the **parent directory**, not the file: editors and formatters write by
rename-over, which destroys the inode and leaves a watch on the file itself pointed at nothing.
This is the single most common way a file watcher is written wrong.

Coalesce bursts — one save produces several events on every platform.

- [ ] **Step 4: commit** — `fix(app): notice when the file changes underneath the editor`

## Task 3: Redraw because something changed

**Files:** modify `crates/typ-app/src/run.rs`, `src/app.rs`, add `crates/typ-app/tests/damage.rs`

`PanelEvent::NeedsRedraw` has been returned by every panel since M1 and **has never done
anything** — the loop repaints unconditionally every pass, so the event is decorative. That is
tolerable while the loop only wakes on keypresses. It stops being tolerable the moment Task 1
lets a worker wake it, because then every wakeup repaints the whole screen.

- [ ] **Step 1 (RED): a wakeup that changes nothing draws nothing**

Assert a frame counter does not advance for an event that changed no state. Then assert it
*does* for a keypress that inserts a character. The counter is test-only scaffolding on the
loop body, not a public API.

- [ ] **Step 2 (GREEN): the dirty flag**

`NeedsRedraw` sets it; drawing clears it. Every `PanelEvent` variant that changes what is on
screen must set it, and the failure mode is a variant that forgets — so make the *default*
setting it, and be explicit about the ones that do not.

- [ ] **Step 3: measure it**

Add a perf case: an idle wakeup, which should now cost approximately nothing. Take the file's
mutex — see AGENTS.md, and the milestone where not doing so produced a phantom 20x regression.

- [ ] **Step 4: commit** — `perf(app): draw because state changed, not because the loop went round`

## Task 4: Resize, and the keystroke the scroll ate

Two defects that are the same defect: the loop's input handling drops things.

**Files:** modify `crates/typ-app/src/run.rs`, add tests

- [ ] **Step 1 (RED): resize repaints**

Defect 10. `Event::Resize` is unhandled and that is harmless *only* because the loop repaints
unconditionally — which Task 3 just stopped doing. Written into this plan rather than
rediscovered as "the screen freezes when I resize the terminal", which is what it will look
like.

Assert a resize event marks the frame dirty and that the panels see the new size.

- [ ] **Step 2 (RED): a key pressed during a scroll is not lost**

Scroll coalescing drains pending events to batch wheel deltas, and anything that is not a
scroll gets `break`ed away and dropped. Flick the wheel and type at the same time and a
character vanishes. Assert that a key arriving mid-burst still reaches the buffer.

The fix is to keep it rather than drop it: coalescing consumes scrolls and pushes anything else
back for the next pass.

- [ ] **Step 3: commit** — `fix(app): handle resize, and stop coalescing from eating keys`

## Task 5: Save without destroying what it did not write

**Files:** modify `crates/typ-buffer/src/buffer.rs`, extend `crates/typ-buffer/tests/`

Deferred from M2.1 and still true. Each of these is a small silent act of vandalism on someone
else's file.

- [ ] **Step 1 (RED): line endings survive a round trip**

M2.3 shipped the detection half and a test for it. This is the other half: open a CRLF file,
edit it, save it, and assert the file is still CRLF. Today every save writes LF and turns the
whole file into a one-line diff.

- [ ] **Step 2 (RED): a symlink is written through, not replaced**

Saving replaces the file, so saving through a symlink replaces the *link* with a regular file.
Dotfile repositories are made of symlinks and this quietly dismantles them.

- [ ] **Step 3 (RED): mode bits survive**

Save a file that is `0755` and assert it still is. An executable script that stops being
executable after an edit is a memorable bug. Unix-only test, `#[cfg(unix)]`.

- [ ] **Step 4 (GREEN), and the durability half**

The atomic-rename save already writes a temp file and renames. Carry the original's metadata
onto the temp file before the rename, resolve symlinks first, and **fsync the parent directory
after** — a rename is not durable until the directory entry is, which is how a crash leaves a
zero-length file where the source used to be.

- [ ] **Step 5: commit** — `fix(buffer): save preserves line endings, symlinks and mode bits`

## Self-review

To be run twice before Task 1, per the practice from M2, M2.2 and M2.3. The second pass is the
one that finds things.

**Spec coverage.** §4 "nothing blocks the render thread": Task 1 is what makes this true rather
than vacuous — today it holds only because nothing runs off-thread. §7 "the event loop blocks on
one channel, with worker threads and a crossterm-pumping thread feeding it": Task 1, verbatim.
§7 "damage-driven redraw, repaint on dirty state, never on a timer tick": Task 3. §7 "input
coalescing, batch scroll deltas, drop stale resize": Task 4 — and note the spec says drop stale
*resizes*, not stale keys, which is exactly the bug.

**Ordering risk.** Task 3 is the one that changes a working editor into a subtly broken one if
any redraw path is missed, and Task 4 exists because Task 3 creates it. They must not be
separated by anything, and Task 4 must not be deferred "because resize looks fine" — it will
look fine right up until it does not.

**Dependency risk.** One new crate, `notify`, and it is the only one this milestone needs. The
version to take is 8.2.0 and not the 9.0 release candidate.

**What would make this plan wrong.** If the channel turns out to need to carry a *reference* to
something the app owns — a buffer, a panel — then `AppEvent` stops being a plain data type and
the whole shape is wrong. The design says workers own their inputs and send owned results, and
the first task that cannot obey that is the one to stop at and rethink rather than to work
around.

**The thing this milestone cannot fix.** It makes the editor live and correct, and it does
nothing for what it can *do*. There is still no syntax highlighting, no LSP, no tabs. That is
M2.5 and M3, and both of them are cheaper for this landing first.
