# M2.2 (Usable) — Implementation Plan

**How to use this plan:** tasks are ordered and each ends with a commit. Work them in sequence;
each leaves the tree working and testable. Checkboxes track progress. Record what actually
happened next to what was expected, on an "Actual:" line, the way the M2 plan does.

**Goal:** make TYPE an editor its author can use to write TYPE. Not more capability — the
capability from M2 is real. This milestone closes the six gaps that make a real editing session
impossible, all of which were found by reading the tree rather than by planning, and none of
which any earlier plan named.

**Why now, ahead of M2.5:** architecture §9 declares self-hosting the forcing function from M2
onward and it has never engaged. Every milestone after this one inherits the blind spot until
it does. See [`../design/gap-analysis.md`](../design/gap-analysis.md) — the audit that found
these — and in particular its "Why the plans could not catch these".

**Spec:** [`../design/architecture.md`](../design/architecture.md) — §4 product principles
(mouse/keyboard parity, every action reachable three ways), §5 the `Panel` contract and the
selection model.

**Prior plan:** [`m2.1-correctness.md`](m2.1-correctness.md). M2 and M2.1 are merged; `main` is
v0.2.1 with 292 tests green on three platforms.

## Global constraints

Every task's requirements implicitly include the M2 plan's "Global constraints". Additionally:

- **Every new primitive is an `Action`.** Clipboard and indent are editing primitives, so they
  are named actions reachable from the keymap, the future palette and the future vim layer —
  not methods hung off a key handler.
- **`Action` stays `Copy`.** It derives `Clone, Copy, PartialEq, Eq, Hash` and the keymap and
  its tests depend on that. No variant may carry a `String`. Task 6 works around this
  deliberately rather than widening the type — see its note.
- **Mouse and keyboard are peers.** Anything reachable one way is reachable both, with a test
  each.
- **Nothing degrades the keystroke budget.** `InsertChar` is at 1.2 ms on a 50k-line file after
  M2.1. Task 5's cap and Task 2's clipboard both sit on edit paths; neither may regress it.

## What M2.2 does not include

No tabs — those are M4, and they change what *opening* means rather than what *guarding* means
(Task 1's guard becomes the per-tab guard there). No tree-sitter, no themes, no event-loop
rework: all M2.5. No replace-one, no regex. The scope is exactly the six defects and nothing
adjacent, however tempting.

## Task 1: Opening a file stops discarding unsaved work

The whole reason this milestone exists ahead of the others: this one loses data today.

**Files:** modify `crates/typ-app/src/app.rs`, add `crates/typ-app/tests/open_guard.rs`

- [x] **Step 1 (RED): a test that loses work**

In a new `tests/open_guard.rs`: build an `App`, open a file, type into it so the buffer is
dirty, then `open_path` a second file. Assert the app did **not** switch buffers and that a
status message names the unsaved file.

Run it. It must fail by *switching anyway* — that is the defect. If it fails any other way, the
test is wrong before the code is.

- [x] **Step 2 (GREEN): guard the replace**

`open_path` consults `self.editor.needs_close_confirmation()` exactly as `request_quit` does. On
`Some(message)`, set the status to that message plus "Ctrl+S to save, or open again to
discard", set a pending flag, and return without switching. The next `open_path` for the same
path goes through.

Reuse the `quit_pending` shape rather than inventing a second one: one pending-confirmation
concept, two triggers. `clear_transient` already expires it on the next keypress, which is the
behaviour we want — a confirmation is answered immediately or not at all.

- [x] **Step 3: the tree's Enter goes through the same path**

`PanelEvent::OpenFile` is handled in `apply` by calling `open_path`, so the guard covers the
tree for free. Add a test that drives it through `handle_chord` rather than calling `open_path`
directly, because that is the path a user takes and the one a refactor could quietly bypass.

- [x] **Step 4: commit**

```
fix(app): opening a file no longer discards unsaved changes
```

**Actual:** Six tests, three of which failed RED for the stated reason —
`left: "second.rs"`, it switched anyway. 298 tests green after, clippy and fmt clean.
Committed `6b19781`.

**Deviation.** The plan said to reuse the `quit_pending` shape as-is: a bool, expired by
`clear_transient`. That does not survive the dispatch order. `handle_chord` calls
`clear_transient` on its way in, so the second keypress — the one repeating the open — erases
the flag it is meant to satisfy, and the open can never go through. The guard now stores
`(PathBuf, u64)`: the path, so confirming one file does not arm every other, and the input
event it was armed on, so it stays valid for exactly the next one and a stale confirmation
answered ten minutes later is not treated as an answer. `clear_transient` counts input events,
which is the one place both keypresses and mouse presses pass through.

Only the test that drove a real keypress through the tree caught this. The four calling
`open_path` directly all passed against the broken version.

## Task 2: The clipboard

Absent entirely today: no `Copy`, no `Cut`, no `Paste`, and `Ctrl+C` does nothing.

**Files:** add `crates/typ-buffer/src/clipboard.rs`, modify `action.rs`, `keymap.rs`,
`actions.rs`, add `crates/typ-panel-editor/tests/clipboard.rs`

### The design, decided here

Three layers, because a terminal editor has to work in three situations:

1. **An internal register**, always present and always the source of truth for paste. Set on
   copy and cut.
2. **The system clipboard via `arboard`**, best-effort. Copy writes to it; paste reads from it
   and falls back to the register when it is unavailable — which is the normal case over SSH,
   in a bare tty, and on a headless box.
3. **OSC 52 on copy.** One escape sequence carrying base64, which the *local* terminal
   intercepts, so copying over SSH lands in the laptop's clipboard rather than the server's.
   This is the thing that makes a terminal editor feel native over a network and it costs about
   ten lines.

**Reading via OSC 52 is not implemented.** The response has to be parsed off the input stream,
and most terminals disable clipboard *reads* by default for good security reasons — a remote
host that can read your clipboard reads whatever you last copied. Paste uses `arboard` then the
register. Note this in the module docs so the asymmetry reads as a decision.

- [ ] **Step 1 (RED): copy, cut and paste across selections**

Tests, all through actions:
- copy leaves the buffer unchanged and the register holding the selected text
- cut removes the selection and leaves the register holding it, as one undo step
- paste at a caret inserts; paste over a selection replaces it
- with three cursors, copy joins the three selections with newlines, and pasting three lines
  into three cursors distributes one line to each — the behaviour VS Code and Sublime both have
  and the reason a multi-cursor copy is not just string concatenation
- pasting a count of lines that does not match the cursor count inserts the whole text at every
  cursor, which is the unsurprising fallback

- [ ] **Step 2 (GREEN): the register and the actions**

`clipboard.rs` holds the register and the `arboard`/OSC 52 plumbing behind two functions,
`set(&str)` and `get() -> Option<String>`. `arboard` failures are swallowed to the register, not
surfaced — a missing system clipboard is a normal condition, not an error worth a status line.

The editor's `perform` gains `Copy`, `Cut`, `Paste`, all built on `begin_edit_group` /
`end_edit_group` so a multi-cursor cut or paste is one undo step. Cut and paste describe edits
the way Task 8 of M2 established; neither invents a second edit path.

- [ ] **Step 3: bindings**

`ctrl+c`, `ctrl+x`, `ctrl+v`, plus `ctrl+insert` / `shift+insert` / `shift+delete` which are
what a good number of terminals actually deliver. Note in the README that a terminal may
intercept `Ctrl+C` before TYPE sees it and that the Insert-key trio is the escape hatch.

`Ctrl+C` no longer being SIGINT-shaped is correct for an editor and matches every non-modal
editor in the field. `Ctrl+Q` remains the quit path.

- [ ] **Step 4: commit**

```
feat(editor): copy, cut and paste, with OSC 52 so it works over SSH
```

## Task 3: Tab indents

**Files:** modify `action.rs`, `keymap.rs`, `actions.rs`, add
`crates/typ-panel-editor/tests/indent.rs`

### The binding conflict, decided here

`tab` is bound to `FocusNext` today and that is the only way to move focus. Tab must indent —
no code editor is usable otherwise — so focus moves to **`F6`**, with **`ctrl+tab`** bound
alongside it.

`F6` is primary rather than `Ctrl+Tab` because without the kitty keyboard protocol a terminal
cannot distinguish `Ctrl+Tab` from `Tab`, and capability detection does not land until M2.5.
`F6` is what browsers and IDEs use for pane cycling and it survives every terminal.

**Accepted consequence:** Tab does nothing in the file tree, where it used to cycle focus. The
tree has no indent concept and no named actions of its own — architecture §5 already records
that naming the tree's primitives is M4 work, arriving with the command palette. `F6` works
from both panels, so nothing becomes unreachable. Revisit at M4, not before.

- [ ] **Step 1 (RED): indent and outdent**

- Tab at a caret inserts to the next tab stop, not a fixed four spaces — a caret at column 2
  with `TAB_WIDTH = 4` moves to column 4, not column 6
- Tab with a non-empty selection indents every line the selection touches and does not replace
  it, which is the difference between an editor and a text box
- Shift+Tab removes one level, and does nothing on a line with no leading whitespace rather
  than eating a character
- outdent handles a partial level: three leading spaces go to zero, not to minus one
- multi-cursor indent is one undo step

- [ ] **Step 2 (GREEN): `Indent` and `Outdent`**

Both operate per *line touched by a selection*, deduplicated — two cursors on one line indent it
once. Selections shift by the amount inserted or removed on their own line, so the selection
survives the operation visibly intact; this is what the M2 `Shift` map is for and it should not
need a new mechanism.

Tabs versus spaces is not configurable in this milestone. Spaces, `TAB_WIDTH` wide, matching
what the renderer already assumes. A config setting lands with `typ-config` at M2.5, and
guessing at its shape now is how it ends up wrong.

- [ ] **Step 3: commit**

```
feat(editor): Tab indents, Shift+Tab outdents, focus moves to F6
```

## Task 4: `typ newfile.md` opens a new file

**Files:** modify `crates/typ/src/main.rs`, `crates/typ-buffer/src/buffer.rs`, add a test to
`crates/typ/tests/` or extend the app's milestone tests

- [ ] **Step 1 (RED)**

`typ` with a path that does not exist must start with an empty buffer whose title is that
filename, and saving must create the file with the typed contents. Today it exits 1 with "does
not exist".

Also assert the failure that must be *kept*: a path whose **parent directory** does not exist
still fails, and fails before the alternate screen is entered, because the alternative is a
user typing into a buffer that can never be saved.

- [ ] **Step 2 (GREEN)**

`main.rs` stops requiring `target.exists()`. If the path does not exist and its parent does,
treat it as a file to be created: root is the parent, and the editor opens an empty buffer with
the path set. `TextBuffer::from_path` gains a sibling — `TextBuffer::new_at(path)` — rather than
teaching `from_path` to invent files, so "read this file" keeps meaning exactly that.

The buffer starts **not dirty**. Nothing has been typed, and marking it dirty would mean
`Ctrl+Q` challenges the user over a file they never edited.

- [ ] **Step 3: commit**

```
feat(cli): typ <newfile> opens a buffer that save will create
```

## Task 5: The undo stack stops growing forever

**Files:** modify `crates/typ-buffer/src/undo.rs`, extend `crates/typ-buffer/tests/undo.rs`

- [ ] **Step 1 (RED)**

Record more than the cap, assert the stack holds at the cap, that the *oldest* entries are the
ones dropped, and that a redo stack banked before the eviction is not corrupted by it.

- [ ] **Step 2 (GREEN)**

`const MAX_UNDO_STEPS: usize = 1000;` and a `VecDeque`, or a `Vec` with a drain from the front —
whichever reads more plainly at this size; the constant is the decision, the container is not.
Ropey's structural sharing makes each snapshot cheap but not free: every one pins the nodes it
replaced, so an unbounded stack is an unbounded retention of every version of the file.

1000 is vim's `undolevels` default and there is no reason to be cleverer than that until
somebody measures a session where it bites.

- [ ] **Step 3: commit**

```
fix(buffer): cap the undo stack at 1000 steps
```

## Task 6: Bracketed paste

A terminal paste currently arrives as N key events: N loop passes, N repaints, one undo step per
character, and any chord inside the pasted text executes as a command instead of being inserted.

**Files:** modify `crates/typ-app/src/run.rs`, `crates/typ-app/src/app.rs`, add a test to
`crates/typ-app/tests/`

### Why this does not add an `Action` variant

`Action` is `Copy`, and `InsertText(String)` would end that — which would touch the keymap, its
tests, and every match in the dispatcher, for one variant.

Instead: the app puts the pasted text into the clipboard register from Task 2 and dispatches
`Action::Paste`. The invariant holds — pasting *is* an action, reachable from the palette and
the vim layer — and the payload travels the way payloads already travel. This is the cheaper
half of the same design and it is worth stating so it does not read as an oversight later.

- [ ] **Step 1 (RED)**

A test that feeds `Event::Paste("hello\nworld")` through the app and asserts both lines land in
the buffer, and that a single `Undo` takes the whole paste back.

- [ ] **Step 2 (GREEN)**

`EnableBracketedPaste` beside `EnableMouseCapture` in `run`, disabled in the same teardown and
in the panic hook — the hook already exists for mouse capture and this is the same class of
failure, a terminal left in a mode the shell does not expect.

`Event::Paste(text)` routes to the register-then-`Paste` path above. When a prompt is open the
text goes into the prompt instead, which is what a user pasting a search term means.

- [ ] **Step 3: commit**

```
feat(app): bracketed paste arrives as one edit, not one per character
```

## Self-review

To be run twice before Task 1, per the M2 plan's practice. The second pass is the one that
finds things.

**Spec coverage.** §4 mouse/keyboard parity: clipboard is keyboard-only in this milestone, and
that is a gap — a right-click context menu or a middle-click primary-selection paste is the
mouse half. Neither is standard enough in a terminal to guess at; **named here as a known
absence rather than an oversight**, revisit when the palette lands at M4. §4 "every action
reachable three ways": all five new actions are keymap rows and all five appear in
`Action::ALL`, so the M2 test `every_default_binding_resolves_to_something_that_handles_it`
covers them without modification.

**Budget risk.** Task 2's copy joins selections into a `String` and Task 3's indent touches
every line a selection covers. Both are proportional to the selection, not the buffer — but
`SelectAll` on a 50k-line file makes them buffer-sized. Measure copy-after-select-all before
closing Task 2; if it exceeds the frame budget it belongs off-thread, and that is M2.5's
machinery, so the honest move would be to note it and let M2.5 pick it up rather than to build
a channel here.

**Dependency added.** `arboard` is the one new dependency. Checked against the workspace: no
existing equivalent. It pulls X11/Wayland bindings on Linux, which is why every clipboard path
degrades to the internal register rather than erroring — a headless box must stay fully usable.

**Ordering risk.** Task 6 depends on Task 2's register, and Task 3 changes a binding the README
documents. Nothing else couples. Tasks 1, 4 and 5 are independent and could be done in any
order; they are first because Task 1 is the one currently losing data.
