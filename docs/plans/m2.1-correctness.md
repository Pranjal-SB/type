# M2.1 (Correctness) — Implementation Plan

**How to use this plan:** tasks are ordered and each ends with a commit. Work them in
sequence; each one leaves the tree in a working, testable state. Checkboxes track progress.

**Goal:** Close the three defects an audit of M2 tasks 1–10 found by measurement, before
Task 13 builds a search box on top of them. Two are budget violations against
architecture §4; one is the missing position-mapping every later milestone needs.

**Why now, before Task 13.** Task 13's search box runs `find_all` on every keystroke and
holds match positions across edits. Both of those are broken today — 87 ms per scan, and no
type that can carry a position across an edit. Building 13 first means building it twice.

**Architecture:** No new concepts. One helper (`with_line_str`) removes whole-buffer
materialization from three hot paths; `History` gains an edit-kind tag and a selection
snapshot; `Shift` moves out of `typ-panel-editor` into `typ-buffer` where the consumers that
need it can reach it.

**Tech stack:** unchanged — Rust 1.96 (edition 2024) · ropey 1.6 · unicode-segmentation 1.11.

**Spec:** [`docs/design/architecture.md`](../design/architecture.md) — §4 performance
budgets, §5 the crate split.

**Prior plan:** [`m2-editing.md`](m2-editing.md). Tasks 1–10 are complete and merged.
Tasks 11–16 resume after this milestone.

## Measured baseline

Release build, 50k-line file (3.2 MB), against the §4 budget of 16 ms p99:

| Operation | Before | Budget |
|---|---|---|
| `InsertChar` — one keystroke | 25.9 ms | 16 ms |
| `Undo` + `Redo` pair | 244 ms | 16 ms |
| `find_all` — one search keystroke | 87.4 ms | 16 ms |
| `Move { Down }` | 3.8 µs | 16 ms |

Root cause of all three: `TextBuffer::line_text` returns an owned `String`, and three
callers loop it over the whole buffer.

In `crates/typ-buffer/src/buffer.rs`, add the borrowing accessor and route every internal
caller through it:

```rust
    /// Call `f` with one line's text, borrowed from the rope when possible.
    ///
    /// `RopeSlice::as_str` succeeds whenever the line lives inside a single
    /// chunk, which is the overwhelmingly common case — ropey chunks are ~1 KB
    /// and lines of code are not. Only a line straddling a chunk boundary pays
    /// for a `String`.
    ///
    /// This exists because `line_text` returning an owned `String` was correct
    /// but quadratic in aggregate: three callers looped it over every line in
    /// the buffer, so one keystroke on a 50k-line file allocated 50k strings.
    /// A borrowing accessor makes the cheap thing the easy thing to reach for.
    pub fn with_line_str<T>(&self, line: usize, f: impl FnOnce(&str) -> T) -> T {
        if line >= self.rope.len_lines() {
            return f("");
        }
        let slice = self.rope.line(line);
        match slice.as_str() {
            Some(s) => f(trim_line_ending(s)),
            None => {
                let owned = slice.to_string();
                f(trim_line_ending(&owned))
            }
        }
    }

    /// Graphemes on a line, without materializing it.
    pub fn line_grapheme_count(&self, line: usize) -> usize {
        self.with_line_str(line, |s| s.graphemes(true).count())
    }
```

with the trimming rule pulled out so both paths share it:

```rust
/// A line without its terminator. Handles CRLF as one unit rather than as two
/// separate trims, so a stray `\r` inside a line is left alone.
fn trim_line_ending(s: &str) -> &str {
    s.strip_suffix('\n')
        .map(|s| s.strip_suffix('\r').unwrap_or(s))
        .unwrap_or(s)
}
```

    ///
    /// Allocates. Prefer `with_line_str` in anything that runs per line over a
    /// range of lines.
    pub fn line_text(&self, line: usize) -> String {
        self.with_line_str(line, str::to_string)

**Three deviations, all from the plan being wrong about where the cost was.**

1. **The 87 ms `find_all` baseline in this plan's header was not comparable.** It was
   measured from a throwaway test in `typ-panel-editor`; the same operation measured from
   `typ-buffer`'s own test binary is 141 ms. The plan's other before-numbers are from the
   editor crate and stand. Corrected in the table above by re-measuring everything in the
   test binaries that were committed.

2. **`with_line_str` made search slower, not faster** — 141 ms → 174 ms. The per-line
   `String` was never search's bottleneck, so removing it bought nothing and the closure
   cost something. The plan asserted a cause it had not measured. Two real causes, found by
   measuring instead:
   - `Rope::line(i)` in a loop is a fresh O(log n) descent per line: **458 ns per line of
     pure overhead**, 23 ms across the file before any searching. `Rope::lines()` walks the
     tree once. This was the dominant cost and the plan never mentioned it.
   - Re-splitting the needle into graphemes per line. Hoisted into `find_all`.

   An intermediate attempt to also drop the per-line haystack `Vec` — re-segmenting from
   each candidate position instead — made it worse again (190 ms), because building a
   `Graphemes` iterator per position costs more than the one `Vec` of borrowed slices it
   replaces. Reverted, with the number recorded in the code so it is not retried.

3. **The `find_all` budget test was rewritten, because the original asserted the wrong
   thing.** A whole-buffer scan returning 50k matches will not fit in a frame at any
   constant factor, and the honest conclusion is not "optimise harder" but "a search box
   must not call `find_all` per keystroke." The gated test now uses a rare needle, which is
   the shape a search box actually produces; the all-match case is measured and printed
   without a gate. This makes viewport-first search a **design constraint on Task 13**, not
   a perf bug to be smoothed over here.

### Task 2: Undo groups a typing run and restores the selections

**Files:**
- Create: `crates/typ-buffer/tests/undo.rs`
- Modify: `crates/typ-buffer/src/undo.rs`, `crates/typ-buffer/src/buffer.rs`,
  `crates/typ-panel-editor/src/actions.rs`, `crates/typ-panel-editor/src/lib.rs`

**Interfaces:**
- Consumes: `typ_buffer::Selections`
- Produces:
  - `typ_buffer::EditKind` — `Insert`, `Delete`, `Other`
  - `TextBuffer::begin_edit_group(&mut self, kind: EditKind, selections: &Selections)`
  - `TextBuffer::undo_boundary(&mut self)`
  - `TextBuffer::undo/redo(&mut self, current: &Selections) -> Option<Selections>`

**Why:** typing `hello` is five undo steps today, and undo leaves the caret wherever
clamping put it. Every editor in the field coalesces a typing run into one step and restores
the selection the edit was made from — vim, VS Code, Zed, Helix, Neovim. This is not a
stylistic difference to defend; it is the behavior users have in their hands.

**The coalescing rule, and why it has no clock.** VS Code and Zed break undo groups on an
idle timer. A timer means the buffer needs a clock, which means tests need to inject one,
which means the rule is only ever tested through a fake. The rule here is structural
instead: consecutive edits of the same `EditKind` coalesce, and anything that is not an edit
— a motion, a click, a save — calls `undo_boundary()`. That is deterministic, testable with
no injection, and matches what a user means by "undo what I just typed": the run ends when
they moved. The ceiling: pausing for ten minutes mid-word without moving still coalesces.
If that ever bites, a timer goes *beside* this rule, not instead of it.

```rust
use ropey::Rope;

use crate::selection::Selections;

/// What an edit did, for the purpose of deciding whether it continues the
/// previous one.
///
/// Coarse on purpose: the question is only "is this the same kind of thing the
/// user was already doing", and a finer taxonomy would split runs the user
/// experiences as one.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum EditKind {
    Insert,
    Delete,
    /// Anything that should always stand alone — a paste, a replace-all.
    Other,
}

/// The buffer as it stood before an edit, and where the cursors were.
///
/// Storing the selections is what makes undo put the caret back where the edit
/// happened rather than wherever clamping left it. Every editor in the field
/// does this; an undo that scrolls you somewhere unrelated is disorienting
/// enough that users stop trusting it.
#[derive(Clone)]
pub struct Snapshot {
    pub rope: Rope,
    pub selections: Selections,
}

/// Whole-content undo history, stored as rope snapshots.
///
/// A snapshot is a `Rope` rather than a `String` because ropey clones are O(1)
/// and copy-on-write: two snapshots share every node they have in common, so a
/// deep undo stack over a large file costs the edits, not one full copy of the
/// text per step.
///
/// Whole-content snapshots stay the right call at this size — they are correct
/// for any edit shape, and with structural sharing they are no longer expensive
/// enough to justify per-edit deltas.
#[derive(Default)]
pub struct History {
    undo: Vec<Snapshot>,
    redo: Vec<Snapshot>,
    /// The kind of the run currently open. `None` means the next edit starts a
    /// new step regardless of its kind.
    open_run: Option<EditKind>,
}

impl History {
    /// Record the state before an edit, unless it continues the open run.
    ///
    /// Continuing a run means *not* pushing: the snapshot already on the stack
    /// predates the whole run, which is exactly the state undo should restore.
    pub fn record(&mut self, kind: EditKind, before: Rope, selections: &Selections) {
        if self.open_run == Some(kind) && kind != EditKind::Other {
            self.redo.clear();
            return;
        }
        self.undo.push(Snapshot {
            rope: before,
            selections: selections.clone(),
        });
        self.open_run = Some(kind);
        self.redo.clear();
    }

    /// End the open run, so the next edit starts a new undo step.
    ///
    /// Called on anything that is not an edit — a motion, a click, a save.
    pub fn boundary(&mut self) {
        self.open_run = None;
    }

    /// Returns the state to restore, banking `current` for redo.
    pub fn undo(&mut self, current: Rope, selections: &Selections) -> Option<Snapshot> {
        let previous = self.undo.pop()?;
        self.redo.push(Snapshot {
            rope: current,
            selections: selections.clone(),
        });
        // An undo always ends the run: typing after an undo must not fold into
        // the step that was just undone.
        self.open_run = None;
        Some(previous)
    }

    pub fn redo(&mut self, current: Rope, selections: &Selections) -> Option<Snapshot> {
        let next = self.redo.pop()?;
        self.undo.push(Snapshot {
            rope: current,
            selections: selections.clone(),
        });
        self.open_run = None;
        Some(next)
    }
}
```

`crates/typ-buffer/src/buffer.rs` — the group methods carry the kind and the selections,
and `undo`/`redo` hand back the selections to restore:

```rust
    /// Begin a group of edits that undo together.
    ///
    /// One snapshot is taken up front and none during the group, so thirty
    /// cursors typing one character is one undo step. Whether that snapshot is
    /// actually pushed is `History`'s call: a group continuing a run of the same
    /// kind folds into it.
    pub fn begin_edit_group(&mut self, kind: EditKind, selections: &Selections) {
        if self.group_depth == 0 {
            self.history.record(kind, self.rope.clone(), selections);
        }
        self.group_depth += 1;
    }

    pub fn end_edit_group(&mut self) {
        self.group_depth = self.group_depth.saturating_sub(1);
    }

    /// End the current undo run. The next edit starts a new step.
    pub fn undo_boundary(&mut self) {
        self.history.boundary();
    }

    /// Undo one step, returning the selections to restore.
    pub fn undo(&mut self, current: &Selections) -> Option<Selections> {
        let snapshot = self.history.undo(self.rope.clone(), current)?;
        self.rope = snapshot.rope;
        self.dirty = true;
        Some(snapshot.selections)
    }

    pub fn redo(&mut self, current: &Selections) -> Option<Selections> {
        let snapshot = self.history.redo(self.rope.clone(), current)?;
        self.rope = snapshot.rope;
        self.dirty = true;
        Some(snapshot.selections)
    }
```

`record_snapshot` — the path used by the standalone `insert_char` / `delete_*` /
`replace_range` helpers when no group is open — needs a kind and a selection set it does not
have. Rather than invent one, those helpers become group-only: `replace_range` no longer
records at all, and callers must open a group. The three M1-era helpers (`insert_char`,
`delete_before`, `delete_after`) are used only by the legacy `handle_key` arms that M2
Task 12 deletes; they open an `EditKind::Other` group with a single caret at the edit site,
which is exactly their old one-step-per-keypress behavior.

### Task 3: The edit shift map moves into `typ-buffer`

**Files:**
- Create: `crates/typ-buffer/src/change.rs`, `crates/typ-buffer/tests/change.rs`
- Modify: `crates/typ-buffer/src/lib.rs`, `crates/typ-panel-editor/src/actions.rs`

**Interfaces:**
- Consumes: `typ_buffer::Position`
- Produces: `typ_buffer::Shift` — `apply(Position) -> Position`, `record(...)`

**Why:** `Shift` is the one thing in the tree that knows how a position moves when the text
before it changes. It is private to `actions.rs`, so the next three consumers that need it —
search results held across an edit (Task 13, next), LSP diagnostics (M3), git hunks (M5) —
each have to rediscover it. Moving it costs one file; retrofitting three consumers later
costs three.

**What this is not.** This is a *shift map*: it maps positions forward through one batch of
edits, in the order they were applied. It is not an anchor system. Zed's `Anchor` and
Neovim's extmarks survive arbitrary later edits because the buffer tracks them; `Shift`
survives exactly one batch and is then discarded. That is enough for every consumer named
above and it is what the code already does correctly. When something needs a position to
survive an arbitrary edit sequence, that is anchors, and anchors are a separate decision.
