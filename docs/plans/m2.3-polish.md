# M2.3 (Polish) — Implementation Plan

**How to use this plan:** tasks are ordered and each ends with a commit. Work them in sequence;
each leaves the tree working and testable. Record what actually happened on an "Actual:" line.

**Goal:** make TYPE *look* like a finished program. M2.2 made it functionally usable and did
nothing for how it reads; the author used it and reported it "feels very prototypey compared to
ttt and TermIDE". This milestone is the answer to that sentence.

**Why it exists at all:** the v0.2.1 audit compared capability — tree-sitter, LSP, git, tabs —
and every row was a feature. None asked whether the thing looks finished. Defects 23–30 in
[`../design/gap-analysis.md`](../design/gap-analysis.md) are the class that audit could not see,
and the largest of them is that **there is no gutter at all**, while `ThemeColors` has carried
an unread `line_numbers` colour since M1.

**Why before M2.5:** every task here is cheap and independent, and M2.5 is the event-loop
rework — the riskiest change in the project so far. Putting the visual wins behind it means the
editor looks like a prototype through the longest and most failure-prone milestone yet. None of
this blocks that work and none of it is blocked by it.

**Spec:** [`../design/architecture.md`](../design/architecture.md) — §4 "Clean" (no chrome
without a job; one visual system across every panel), §5 the `Panel` contract, §7 render model.

**Prior plan:** [`m2.2-usable.md`](m2.2-usable.md). `main` is v0.2.2, 342 tests green on three
platforms.

## Global constraints

Every task's requirements implicitly include the M2 plan's "Global constraints". Additionally:

- **Nothing blocks on M2.5.** No task here may require a wakeable event channel or damage
  tracking. Anything that does belongs in M2.5 and is named at the bottom of this plan.
- **Every new colour is a theme field**, never a literal in a render function. The theme is
  about to become a loadable file at M2.5 and a colour hardcoded now is a colour missed then.
- **Truecolor with a documented fallback.** `Color::Rgb` throughout; capability detection lands
  at M2.5, so until then the fallback is whatever ratatui does with an RGB colour on a 256-colour
  terminal. Do not gate anything on detection that does not exist yet.
- **The render path stays proportional to the viewport.** Everything here draws per visible
  line. Nothing may introduce a whole-buffer scan — see Task 5's note on the one that tries to.

## What M2.3 does not include

No tree-sitter, no themes-as-files, no capability detection, no event-loop work: all M2.5.
No tabs, splits, resizable panels, command palette, or tree file operations: all M4. Defects 31
(file watching) and 34 (`.editorconfig`) are named here and deliberately deferred — see
"Deferred, deliberately".

## Task 1: The gutter

The largest single cause of "prototype" and the one with an architecture question inside it.

**Files:** add `crates/typ-panel-editor/src/gutter.rs`, modify `lib.rs`, `render.rs`, add
`crates/typ-panel-editor/tests/gutter.rs`

### The design, decided here

**A list of components, not a line-number column.** Helix's `helix-view/src/gutter.rs` is
`GutterType::{LineNumbers, Diagnostics, Diff, Spacer, CodeActionHint}` — each with a `width()`
and a renderer, order configurable. Diagnostics arrive at M3 and git-diff markers at M5, and
both want that column. Building a hardcoded gutter now lands the feature and loses the design,
and the second component is what forces the rewrite.

M2.3 ships `LineNumbers` and `Spacer`. `Diagnostics` and `Diff` are enum variants with a
`width()` of 1 and a renderer that draws nothing, so M3 and M5 fill in a function rather than
restructure a module.

- [x] **Step 1 (RED): width and content**

- the gutter is as wide as the digit count of the last line, plus padding — a 9-line file uses
  one digit, a 10-line file two, a 100k-line file six
- the width does not jump as you scroll: it is computed from the buffer's last line, not from
  the highest line currently visible, or the text shifts sideways at line 100
- line numbers are 1-based, matching every compiler error and every other editor
- the cursor's line is styled differently from the others
- the text area shrinks by exactly the gutter width, and clicking still lands on the right
  grapheme — this is the one that breaks silently

- [x] **Step 2 (GREEN): `Gutter` and its components**

`GutterComponent::{LineNumbers, Spacer, Diagnostics, Diff}`, a `Gutter` holding an ordered
`Vec`, `width()` summing the components, and a `render_line(line, is_cursor_line)` returning
spans. `EditorPanel` owns one and subtracts its width before computing the text area.

**The trap:** `handle_mouse` and `cursor_position` both convert between screen cells and
buffer positions using the inner area. Both must account for the gutter or every click lands
`gutter_width` graphemes to the left. Task 1's test list has an explicit case for it because
this is exactly the kind of thing that passes every unit test and is wrong the moment a human
clicks.

- [x] **Step 3: relative line numbers, behind a field**

`LineNumbers { relative: bool }`. Off by default — TYPE is non-modal by default and relative
numbers are a modal-editing idiom — but the field exists so the vim layer can flip it rather
than replace the component.

- [x] **Step 4: commit** — `feat(editor): a composable gutter, with line numbers in it`

**Actual:** 15 gutter tests, 357 workspace tests green, clippy and fmt clean. The RED step
failed for the stated reason — `could not find gutter in typ_panel_editor` — and the trap the
plan named was real: **18 existing tests across 6 files broke**, every one by exactly the
gutter's two cells.

**Deviation 1 — the fix for the trap is one function, not two call sites.** The plan said
`handle_mouse` and `cursor_position` must both subtract the gutter. They must, but saying so
leaves a third caller unnamed: `render` computed its own inner area, so there were three
places converting between screen cells and buffer positions and the plan knew about two.
`text_area` was a static `fn text_area(area: Rect)`; it is now `fn text_area(&self, area)`,
subtracting the gutter, and all three go through it. Making it an instance method is what
makes the omission impossible rather than merely documented — a fourth caller cannot get it
wrong without going out of its way.

**Deviation 2 — the gutter is a second `Paragraph`, not spans prepended to the line.**
Prepending would have put the numbers inside the horizontally-windowed text, so scrolling a
long line sideways would have scrolled the numbers off with it.
`the_number_column_does_not_scroll_sideways_with_the_text` is that test.

**Deviation 3 — `self.width` now means the *text* width.** It feeds `scroll_to_cursor`, so
leaving it as the full inner width would have let the cursor hide behind the right border
before scrolling kicked in, by exactly the gutter's width.

**On the 18 broken tests.** All were geometry, none behaviour, and the fix was applied at the
helper where each file had one — `text_cell` in `clipboard.rs`, `at` in `mouse.rs`, a new `tx`
in `selection_render.rs`. That geometry has now moved twice, borders at M1.1 and the gutter
here, and both times every test carrying a raw column literal was wrong at once. The helpers
are the fix for the third time.

**Cursor-line styling needs no new theme field yet.** The current line uses `theme.fg` and the
rest `theme.line_numbers` — the field M1 wired and never read. That maps onto Task 2's
`line_number_fg` / `line_number_current_fg` without a render change.

## Task 2: A real theme surface, in truecolor

**Files:** modify `crates/typ-core/src/panel.rs`, and every render site that reads a colour

- [x] **Step 1: expand `ThemeColors`**

Ten flat fields becomes a surface with the scopes the next three milestones need. Modelled on
Helix's `ui.*` namespace, which is 40+ scopes; TYPE takes the ones it has a use for now or at
M3, and no more:

```
fg bg
cursor_line_bg
gutter_fg gutter_bg  line_number_fg  line_number_current_fg
selection_bg selection_fg  selection_primary_bg
bracket_match_fg bracket_match_bg
border border_focused
status_bar_bg status_bar_fg  status_bar_inactive_fg  status_bar_accent
tree_directory_fg tree_file_fg
diagnostic_error diagnostic_warning diagnostic_info diagnostic_hint
```

The diagnostic colours ship unused. They are four lines, M3 needs them, and a theme file
written at M2.5 without them is a theme file that gets a breaking change at M3.

- [x] **Step 2: truecolor**

Every value becomes `Color::Rgb`. There is not one `Color::Rgb` in the tree today, so TYPE
currently inherits whatever blue the user's terminal defines and cannot be tuned at all.

Pick one dark theme deliberately and write down *why* those values — architecture §4 asks for
"one visual system applied uniformly", and a palette assembled colour-by-colour as each widget
needed one is how that promise gets broken quietly.

- [x] **Step 3: no colour literals outside the theme**

Grep for `Color::` outside `panel.rs` and drive it to zero. A colour hardcoded now is a colour
missed when the theme becomes a file at M2.5.

- [x] **Step 4: commit** — `feat(ui): a truecolor theme with the scopes M3 will need`

**Actual:** 24 fields, all `Color::Rgb`, 13 new theme tests, 370 workspace tests green.

**The palette is checked, not eyeballed.** `typ-core/tests/theme.rs` computes WCAG 2.1
relative luminance from the actual channel values and asserts floors: body text at 7:1, the
gutter at 3:1, text on either selection at 4.5:1, every diagnostic at 4.5:1. It also asserts
the *relations* that make the system a system — the focused border is brighter than the
unfocused one, the current line's number is brighter than the rest, the cursor-line highlight
is under 1.5:1 against the page so it is felt rather than seen. A palette is the one part of
an editor where "looks fine to me" is the usual standard of proof, and it is the wrong one.

**Deviation 1 — the palette is a named ramp, not a colour per field.** `mod palette` holds
nine neutral steps at one hue (~218°) plus four accents, and `ThemeColors::default()` names
steps. Architecture §4 asks for "one visual system applied uniformly"; picking a colour per
widget is how that promise breaks quietly, since nothing is ever individually wrong.

**Deviation 2 — `cursor` was dropped rather than converted.** It was the *second* field
modelled at M1 and never read, and unlike `line_numbers` it is unreadable by construction: the
terminal owns the cursor's colour. Setting it would mean emitting OSC 12 and changing terminal
state TYPE does not own.

**Deviation 3 — `status_bar_inactive_fg` needed its own ramp step.** Reusing the line-number
grey put it at 2.93:1 against the status bar, under the 3:1 floor. `BASE_05` exists because
the test said so, not because the ramp was designed with nine steps up front.

**Two fields were wired that the task did not mention**, because leaving them unread would
have reproduced the exact defect this task exists to fix: `tree_directory_fg` and
`tree_file_fg` now colour the tree, so the shape of a project is readable without reading the
names. The tree's selected row took `selection_primary_bg` — it has exactly one selection and
it is the thing being steered, the same job the editor's primary does.

**The audit, worth re-running at Task 8.** Colour literals outside `panel.rs`: zero. Fields
still unread: `cursor_line_bg`, `bracket_match_*` (Task 3), `status_bar_inactive_fg`,
`status_bar_accent` (Task 4), `diagnostic_*` (M3). Every one has a named owner — which is the
difference between a reserved field and the `line_numbers` defect.

```bash
rtk proxy grep -rn 'Color::' crates/ --include=*.rs | grep '/src/' | grep -v panel.rs
```

## Task 3: Current line, primary selection, matching brackets

Three small render changes that together are most of what "designed" looks like.

**Files:** add `crates/typ-buffer/src/brackets.rs`, modify `render.rs`, add tests

- [x] **Step 1 (RED): the current line is visible**

The cursor's line gets `cursor_line_bg` across the full width, including past the end of the
text. A highlight that stops at the last character looks like a bug rather than a feature.

With multiple cursors, every cursor's line is highlighted — the alternative is picking one and
making the other twenty-nine invisible.

- [x] **Step 2 (RED): the primary selection is distinguishable**

`selection_primary_bg` for the primary, `selection_bg` for the rest. Helix themes
`ui.selection.primary` separately for exactly this reason: every motion is relative to the
primary, and with thirty cursors TYPE currently gives no way to tell which one that is.

- [x] **Step 3 (RED): matching brackets**

`brackets.rs`: given a position, find the match for the bracket under or immediately before the
cursor. Both are highlighted with `bracket_match_*`.

- scans outward from the cursor, not from the start of the buffer — the search is bounded by
  the viewport plus a small margin, and gives up rather than scanning 50k lines
- nesting counts, so the match for the outer `(` is not the first `)` it meets
- brackets inside strings and comments are wrong without a syntax tree; **this is a known
  limitation until M2.5** and belongs in the module docs rather than in a bug report later
- no match found renders nothing, silently

- [x] **Step 4: commit** — `feat(editor): current-line highlight, primary selection, bracket match`

**Actual:** 14 bracket tests, 10 render tests, 394 workspace tests green. Both RED steps failed
for their stated reasons.

**Deviation 1 — `styled_line` takes a struct, and the precedence is a type.** Three effects on
top of selections put the signature at nine arguments, which is a row of unlabelled values
where swapping two `usize`s compiles cleanly and renders wrong. It now takes a `LineStyle`, and
the per-cell decision is a `Paint` enum with one `paint_for` deciding it: selection beats
bracket beats cursor-line beats plain. Spelling that out as a type rather than a chain of `if`s
inside the run-accumulating loop is what makes it reviewable, and syntax highlighting at M2.5
adds a variant instead of another branch.

**Deviation 2 — a line with a real selection does not also get the stripe.** The plan said
every cursor's line is highlighted. Literally applied, selecting a paragraph paints a stripe
behind the selection as well: two answers to one question. Only *empty* selections tint their
line now, which is what VS Code does and for the same reason.

**Deviation 3 — the current-line tint stops at the gutter.** The line number already marks the
current line there. Helix has a separate `ui.gutter.selected` scope for this and TYPE can add
one when something asks for it; painting the gutter with the text's tint would have been a
guess dressed as consistency.

**Angle brackets are excluded, deliberately.** `<` is a comparison far more often than a
bracket, and highlighting it as one is wrong more often than right.

**The known limitation is in the module docs, not a future bug report.** The scan has no idea
what a string or a comment is, so the `(` in `"a ( b"` counts. That needs the syntax tree, and
`brackets.rs` says so plus what the fix looks like: a predicate for "is this position code",
with the scan otherwise unchanged.

**Two render perf tests added, which the plan did not ask for.** Tasks 1–3 put a gutter, a
bracket search and a per-grapheme paint decision on the render path, and *nothing measured
rendering at all* — architecture §4 budgets keystroke **to painted glyph**, so a keystroke
measured without its repaint is half a number. Measured on a 50k-line file at
`--release --ignored`:

| Operation | Measured | Budget |
|---|---|---|
| Draw a frame, scrolled to the end of a 50k-line file | **439 µs** | 16 ms |
| Draw a frame with an unmatched bracket under the cursor | **375 µs** | 16 ms |

The second is the pathological case for this task: the search runs to its bound every frame.
It is the test that would notice if the bound were ever removed.

## Task 4: The status bar says something

**Files:** add `crates/typ-app/src/status.rs`, modify `app.rs`, add tests

- [x] **Step 1: segments**

Today: message, filename, `line:col`. Helix's statusline has 24 reorderable elements; ttt puts
git blame and an indent picker in its own. TYPE ships the ones it can answer honestly today:

| Segment | Content | Note |
|---|---|---|
| Message / hint | as now | |
| File name + modified | as now | |
| Filetype | from the registry | the registry already resolves it and nothing displays it |
| Line ending | `LF` / `CRLF` | needs the detection deferred from M2.1 — see below |
| Indent | `Spaces: 4` | honest: it is hardcoded, and saying so is the first step to fixing it |
| Selection count | `3 cursors` when >1 | |
| Position | `line:col` as now | |
| Percentage | `42%` | |

**Architecture §5 already plans `status_segments()` for M4** — clickable chips contributed by
the focused panel, routed back by id. That is a better design than a central list, because a
panel owns what it can say about itself. **This task does not build that mechanism.** It fills
the existing status bar with content, structured so that M4 moves the *source* of each segment
into its panel without rewriting what they say.

- [x] **Step 2: line-ending detection**

`m2.1-correctness.md` deferred "line endings not preserved" to M2.5. Displaying `LF`/`CRLF`
needs only the *detection* half, which is ten lines and independent of the preservation half.
Do the detection here, display it, and leave preservation to M2.5 — with a test asserting the
detected value, so M2.5 has something to build against.

- [x] **Step 3: commit** — `feat(app): a status bar that says what file this is`

**Actual:** 8 line-ending tests, 12 segment tests, 414 workspace tests green. The bar went from
three things to seven: `main.rs  rs  LF  Spaces: 4  1:1  33%`.

**Deviation 1 — the filetype is the extension, not a language name.** The task said "from the
registry", but `Registry::handler_for` returns a `HandlerId` and every text file resolves to
`HandlerId("editor")` — displaying that would have shown the word "editor" beside every file.
A name table (`rs` → `Rust`) is the obvious alternative and is exactly the kind of small
addition that becomes a maintenance surface. At M2.5 the honest answer arrives free: the
filetype *is* the tree-sitter grammar that claimed the file. Showing the extension now means
replacing one line then rather than deleting a table.

**Deviation 2 — emphasis, which the task did not mention.** Seven segments in one strip of
small text is worse than three unless the reader can rank them, so each segment carries
`Emphasis::{Normal, Quiet, Accent}`: identity and position normal, facts-that-only-matter-when-
wrong quiet, and *unusual state* accented — an unsaved file, or a cursor count above one. This
is also what makes `status_bar_inactive_fg` and `status_bar_accent` read fields rather than
reserved ones.

**Deviation 3 — the dirty marker moved from the title to colour.** `title()` still carries `*`
for the panel border; the status bar draws the same state as an accented filename. Two
renderings of one fact, each suited to where it sits.

**A one-line file is 100%,** not 1%. Any other arithmetic there is a number pretending to be
information.

**Line endings: the first terminator in the file decides.** A mixed file is not a third kind of
file, and taking a majority would mean a save that silently rewrites every line break in
somebody's file because the count went the other way. A lone `
` is explicitly *not* an
ending — classic Mac endings died with Mac OS 9 and a stray carriage return inside a line is
far likelier. `save` still writes LF; preserving is M2.5's half, and it now has a tested
detector to build on.

**Sixty columns is not enough for both halves,** and the existing truncation rule handles it —
the right-hand segments are the fixed cost and the hint is cut to fit, so a message can never
push the position off the end. The golden frame records what tight looks like.

## Task 5: Select next occurrence

The most-used multi-cursor idiom in the field, and TYPE has the rarer half instead.

**Files:** modify `action.rs`, `keymap.rs`, `actions.rs`, add tests

- [x] **Step 1 (RED)**

`Ctrl+D` — with a selection, find the next occurrence of that text and add a cursor there. With
an empty selection, select the word under the cursor first, so the first press means "select
this word" and the second means "and the next one". That two-stage behaviour is what VS Code,
Sublime and ttt all do and what makes the key feel like one gesture.

`Ctrl+K L`— wait: TYPE has no chord sequences. Bind select-all-occurrences to `ctrl+shift+l`,
which is VS Code's binding, and note that chord *sequences* are a keymap feature that does not
exist yet and is not needed for this.

- wraps to the top of the buffer
- stops adding when every occurrence is selected rather than looping forever
- the search is case-sensitive, unlike `Ctrl+F` — matching an identifier is not the same job as
  finding prose, and every editor in the field draws that line the same way

- [x] **Step 2 (GREEN)**

Built on `SearchQuery` and `find_all`, which already exist.

**The budget trap, stated here so it is not discovered later:** `find_all` scans the whole
buffer, measured at ~10 ms on 50k lines. `Ctrl+D` held down is one scan per press. It is within
budget for a keypress and it is *not* within budget as a hot loop, and the honest fix — search
from the cursor and stop at the first hit — is also the simpler one. Do that rather than
filtering a whole-buffer result.

- [x] **Step 3: commit** — `feat(editor): Ctrl+D selects the next occurrence`

**Actual:** 10 `find_next` tests, 12 occurrence tests, 436 workspace tests green.

**The budget trap, avoided and measured.** The plan said to search from the cursor rather than
filter a whole-buffer `find_all`, and that is what `TextBuffer::find_next` does. Held down on a
50k-line file, `Ctrl+D` costs **3.89 µs per press** against the ~7 ms a filtered `find_all`
would have cost — about 1800x, and the difference between a key you can hold and one you
cannot.

**Deviation — the two-stage behaviour belongs to `Ctrl+D` only.** The plan described one helper
that selects the word under a caret and then searches. Applied to both actions that makes
`Ctrl+Shift+L` take *two* presses to select all occurrences, which is not what anyone means by
the phrase. Three of twelve tests failed on exactly that. Split into
`select_word_under_caret() -> bool` and `occurrence_needle()`: `Ctrl+D` stops when the first
returns true, select-all carries straight on.

**Wrapping is the stop condition, not a convenience.** Coming back round to a match the caller
already holds is how `Ctrl+D` knows every occurrence is selected. Without it the action either
loops forever or stacks duplicate cursors on one word — `it_stops_once_every_occurrence_is_selected`
presses ten times at two occurrences and asserts two.

**`Ctrl+K L` is still unavailable** and the plan was right about why: TYPE has no chord
*sequences*. `ctrl+shift+l` is VS Code's other binding for the same thing, and chord sequences
remain a keymap feature nobody has needed yet.

## Task 6: Goto line

**Files:** modify `action.rs`, `keymap.rs`, `prompt.rs`, `app.rs`, add tests

- [x] **Step 1 (RED)**

`Ctrl+G` opens the status-bar prompt asking for a line number; Enter jumps and centres it in the
viewport. Out-of-range clamps to the last line rather than erroring — the user meant "the end".
Non-numeric input is rejected without closing the prompt.

The prompt machinery from M2 Task 13 already supports this shape; this is a third `PromptKind`,
not a new mechanism.

- [x] **Step 2: commit** — `feat(app): Ctrl+G jumps to a line`

**Actual:** 10 tests, 446 workspace tests green. The plan was right that this is a third
`PromptKind` and not a new mechanism.

**Deviation 1 — the jump centres the line, and `scroll_to_cursor` could not do it.** That
method moves the *minimum* needed, which after a jump leaves the target on whichever edge it
entered from — technically visible and useless, since you jumped there to read around it.
`goto_line` sets `top_line` to put the target mid-viewport and then calls `scroll_to_cursor` to
clamp.

**Deviation 2 — a rejected answer keeps its input.** The plan said non-numeric input is
rejected without closing the prompt. It did not say what happens to the text, and the obvious
implementation clears it, so one bad character means retyping the number from scratch. The
prompt gained `restore_input` and there is a test named for the behaviour.

**The M2 guard test earned its place again.** `every_default_binding_resolves_to_something_that_handles_it`
failed with `["goto_line"]` — it walks `Action::ALL` and reports any action reaching neither
the editor nor the app. Its exemption list is a second copy of "which actions the app owns", so
it is now a named `APP_OWNED` const with a comment saying that adding an app action means
adding a line, rather than a `matches!` arm buried in a filter.

## Task 7: Logging

**Files:** add `crates/typ-app/src/log.rs`, modify `main.rs`

- [x] **Step 1**

A TUI owns the screen, so `println!` debugging is unavailable *by construction* — the one place
logging is not optional is the one place TYPE has none. TermIDE has a whole `logger` crate.

Smallest thing that works: a `TYP_LOG` environment variable naming a file, a `log!` macro that
is a no-op when unset, and a line format of timestamp, level, module, message. No `tracing`, no
subscriber, no async — a file and a mutex. Add the dependency when something measurably needs
it.

Write the first real call sites while the reason is fresh: config load failures, clipboard
provider detection (which provider was chosen — the single most useful line when someone
reports copy not working), and save errors.

- [x] **Step 2: commit** — `feat(app): a log file, for when the screen cannot be printed to`

**Actual:** 7 tests, 453 workspace tests green, and verified through the real binary rather
than only its unit tests.

**Deviation 1 — the clipboard cannot log, so it reports instead.** The plan named clipboard
provider detection as a call site and put `log.rs` in `typ-app`. `typ-buffer` sits *below*
`typ-app` and cannot reach it — the dependency runs the other way and should. So
`clipboard::provider_name()` returns the chosen provider and the binary logs it at startup.
That is the right direction for the dependency and arguably for the decision: the library
reports what it did, the application decides whether anyone is told. **The ceiling:** the first
time something below `typ-app` genuinely needs to log, this becomes a `typ-log` crate with no
dependencies — which is what TermIDE has and what gap-analysis defect 32 cites.

**Deviation 2 — found by running the binary, not by testing it.** Logging initialised after
argument handling, which read fine and meant the one path that most needs an entry wrote
nothing: `typ /nonexistent/file` exits non-zero and takes `$EDITOR`'s caller down with it.
`init_from_env()` is now the first statement in `real_main`, and the resolve failure logs
before it propagates. Seven passing unit tests did not notice, because they all called `init`
directly.

**Deviation 3 — three macros, not one.** `log_info!`/`log_warn!`/`log_error!` over
`log_at!`, so a level is never a positional argument that can be passed wrong. All four are
`#[macro_export]`, so the level check happens before `format!` runs and a disabled log costs a
relaxed atomic load and a branch.

Verified end to end:

```
$ TYP_LOG=/tmp/typ.log typ /nonexistent/dir/file.rs ; echo $?
typ: /nonexistent/dir/file.rs does not exist
1
```

## Self-review

To be run twice before Task 1, per the practice from M2 and M2.2. The second pass is the one
that finds things.

**Spec coverage.** §4 "Clean — no chrome without a job": a gutter earns its cells by making
every compiler error clickable-by-eye, and the status segments each answer a question a user
actually asks. §4 "one visual system applied uniformly": Task 2 is the whole point, and Task 2
Step 3's grep for stray `Color::` is what keeps it true. §4 mouse/keyboard parity: Task 1 Step 2
flags the click-offset trap explicitly, which is the only place this milestone can break it.

**Budget risk.** Task 3's bracket matching and Task 5's occurrence search are the two things
here that can scan more than a viewport. Both have a stated bound in their task. Nothing else
touches more than the visible lines.

**Ordering risk.** Task 2 changes `ThemeColors`, which every render site reads, so it touches
the most files. Doing it *after* Task 1 means the gutter is written against the old struct and
edited once; doing it first means guessing which fields the gutter needs. Task 1 first is the
cheaper order, and the gutter's colours are the two fields most obviously required.

**The thing this milestone cannot fix.** None of it makes the editor *fast* or *live* —
unconditional redraw, a blocking loop, no file watching, no syntax tree. It makes TYPE look
finished while remaining, underneath, a prototype in exactly the way M2.5 addresses. That is the
right order only because the visual work is cheap and independent; it would be the wrong order
if any of it were expensive.
